# Database [Where your data lives, and when it's rebuilt]

## Development

Without `DATABASE_URL`, `pnpm dev` starts Postgres 17 in a container (Docker or Podman, whichever is installed),
one per project directory, kept between runs. `pnpm clean` deletes it.

With `DATABASE_URL` set, in `.env` or the environment, it uses that database instead and never starts a container.

```bash [.env]
DATABASE_URL=postgres://user:password@localhost:5432/postgres
```

## Schemas

Your tables live in a Postgres schema. `dev` names it after the project directory (`my-indexer` → `my_indexer`).
`start` and `serve` need you to name it, with `--schema` or `DATABASE_SCHEMA` (or `schema` in the config), so
production never guesses:

```bash
pnpm start --schema my_indexer_v2
```

kasbah also keeps its progress in that schema (table `_kasbah_meta`), so one database can hold many
apps, or many versions of one app, side by side.

## One indexer per schema

An indexer holds its schema while it runs, as in Ponder: it marks it in `_kasbah_meta` and refreshes that
mark every 10 seconds. A second indexer on the same schema waits once for the mark to expire, then stops:

```text
schema "my_indexer" is in use by another indexer: stop it, or use another --schema (DATABASE_SCHEMA)
```

A clean stop (Ctrl-C, `SIGTERM`) releases it at once. After a crash, the mark expires in 25 seconds and the next
indexer takes over where the crashed one stopped. `clean` refuses a schema a running indexer holds.

## Builds

A build is what decides which rows get written:

- the config's contracts (address or factory, ABI, `startBlock`, `endBlock`, `filter`, `include`) and `blocks`, and
  the chain;
- your tables;
- the files under `src/`, except `src/api/` and tests (`*.test.ts`, `*.spec.ts`).

Editing an API route, or a setting such as `rpc`, `concurrency` or the port, keeps the build and the indexed data. A
helper your handlers import counts only if it lives under `src/` (outside `src/api/`). Change any part of the build and
it changes:

- `dev` drops the schema and indexes again from scratch.
- `start` refuses to run over data from another build:

```text
schema "my_indexer" holds another build of this app (config, tables or handlers changed); run with reset
```

Run the new build in a new schema (see [Self-hosting](/docs/production/self-hosting#one-schema-per-deploy)), or pass
`--reset` to drop the old data first.

`dev` and `start` keep apart: `dev` refuses a schema `start` made (it would drop it on the next change), and `start`
drops a schema `dev` made and indexes from scratch.

## Direct SQL

You can read the tables with any Postgres client:

```sql
SET search_path TO my_indexer;
SELECT id, swaps FROM pools ORDER BY swaps DESC LIMIT 10;
```

- Columns are snake_case: a key `sqrtRatio` is the column `sqrt_ratio`.
- Read only. Writes from outside are not undone on a reorg, and the next build doesn't keep them.
- Primary keys and indexes are created once the backfill is done, so queries during the backfill scan whole tables.
- The schema changes when you deploy a new build in a new schema: point your client at the new one.
